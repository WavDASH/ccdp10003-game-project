==================================================
BUILD GOAL
==================================================

Build a minimal but playable Godot 4.6 prototype of a 2D puzzle-platformer with timeline branching and visible echo cooperation.

The prototype must be directly openable and testable in Godot 4.6.

Use placeholder visuals only.
Do not spend effort on final art, sound, menus, or polish beyond what is needed for mechanic clarity.

==================================================
CORE GAMEPLAY TO IMPLEMENT
==================================================

- A single active player can move left/right and jump.
- Press R to invert time direction.
- Press R again to switch direction again and create a new branch.
- Previous branches remain as semi-transparent echoes.
- Echoes replay recorded movement/actions from their branch.
- Echoes can help solve puzzles.
- Echoes do NOT physically collide with the active player.
- Echoes can collapse if their recorded path becomes invalid in the current world state.
- Echo collapse does NOT fail the level.
- Only active player death fails the level and restarts the current level from the beginning.
- Reverse-time mode must be visually distinct from forward-time mode.
- Different echo generations must be visually distinguishable.

==================================================
IMPORTANT IMPLEMENTATION CORRECTIONS
==================================================

1. PIVOT-TICK SEMANTICS MUST BE EXPLICIT AND CONSISTENT
You must define and implement a clear rule for what happens on the exact physics tick when R is pressed.

This must include:
- whether the current frame is recorded before or after reversal
- when the active branch is sealed
- whether the new branch starts on the same tick or the next tick
- whether branch ranges are inclusive or half-open

Choose one clean rule and apply it consistently everywhere.
Document it clearly in code comments and/or in IMPLEMENTATION_NOTES.md.

Avoid ambiguous off-by-one behavior.

2. DO NOT RELY ON AREA2D SIGNALS FOR TELEPORTING ECHOES
Echoes are replay puppets and may be repositioned directly each physics tick.
Because of that, do NOT build the core system around fragile body_entered/body_exited behavior for echoes.

Use a unified manual-query approach for echo-related detection wherever needed, especially for:
- echo collapse checks
- pressure plate activation by echoes
- hazard checks for echoes

If Area2D is used for some active-player interactions, keep the logic coherent and robust, but echo logic should be based on deliberate physics overlap queries rather than assuming signals will always be reliable.

3. CREATE A DEDICATED ECHO VALIDATION PIPELINE
Implement a dedicated validation path such as:
- validate_echo_path_at_tick(...)
or a similarly named system

This should be the single place that determines whether an echo remains valid.

For MVP, it should at least support:
- overlap with solid static world
- overlap with closed door / blocking gate
- overlap with hazard

It should also be structured so ground-loss / support checks can be added later without redesigning the system.

4. SIMPLIFY COLLISION LAYER SEMANTICS
Keep collision layers semantically clear.

Do not mix doors and static world in a confusing way if it makes debugging harder.
Prefer a clean separation such as:
- static world
- active player
- echoes
- interactable triggers
- hazards
- blocking doors / gates

The system should be easy to extend later.

5. ADD DEBUG READABILITY
The HUD/debug info should not only show direction and tick.
Also show enough information to make debugging branching readable, such as:
- current branch ID
- current generation / reversal count
- current direction
- current tick
- active echo count

This can be simple text, but it should help understand what is happening.

6. PREPARE FOR FUTURE LIMITS
Even if the MVP does not enforce them yet, the code structure should already expose configurable hooks for:
- max reversal count
- max rewind duration per reversal
- max active echoes

These can default to “disabled” or permissive values for now, but the structure should be ready.

FIRST PLAYABLE TEST LEVEL REQUIREMENT
==================================================

The first level should NOT be an arbitrary level.
It must be built around this very clear introductory puzzle:

- There are two switches at different vertical heights:
  - one lower switch
  - one upper switch
- There is a door/gate above that only opens while two valid actors are standing on both switches simultaneously
- The player must cooperate with an echo to keep both switches activated at the same time
- This level should clearly teach the idea:
  “I can use a previous version of myself to help open the path”

Keep this first level readable and not overly punishing.
Do not make it too timing-heavy or too difficult.
It is meant to prove and teach the core mechanic.
